# Database and manual CRUD guide

This application uses PostgreSQL 16 and Prisma. The browser never connects to
PostgreSQL directly: the Node API at `http://localhost:3001` is the only normal
application client. Direct SQL is appropriate for administration, repair, and
reporting; use the API for normal product behaviour because it validates input,
hashes passwords, applies roles, and writes activity logs.

## Start locally

1. Install Docker Desktop (or Docker Engine) and Docker Compose.
2. Copy `.env.docker.example` to `.env` and set strong values.
3. Build and start the complete stack:

   ```bash
   docker compose up --build -d
   ```

No host-side Node, Vite, or npm process is needed. Apache serves the compiled
frontend and proxies `/api/*` internally to the API container.

## Service source locations

| Location | Responsibility |
| --- | --- |
| `web_service/` | React UI, Vite configuration, Apache configuration, and web Dockerfile |
| `api_service/` | Express routes, session handling, and API Dockerfile |
| `db_service/prisma/` | Prisma schema and migrations |
| `docker-compose.yml` | Root-level orchestration, network, and persistent volume |

## Run the complete stack in Docker

For a self-contained deployment with Apache, API, and PostgreSQL containers:

```bash
cp .env.docker.example .env
# Edit .env and set strong POSTGRES_PASSWORD and SESSION_SECRET values.
docker compose up --build -d
```

The application is then served by Apache at:

```text
http://<server-ip>:${WEB_PORT:-9091}/
```

Apache listens on container port 80 and maps it to host port `WEB_PORT` (9091
by default). It serves
the compiled React files and reverse-proxies `/api/*` to the private `api`
container. PostgreSQL is private to the Compose network and persists data in
the `app_postgres_data` volume. The API container runs `prisma db push` during
startup so the schema is available on a new volume; for production release
pipelines, replace this with reviewed `prisma migrate deploy` migrations.

The default deployment is HTTP on port 9091, so `COOKIE_SECURE=false` is
required for the browser to retain the session cookie. After configuring HTTPS,
set `COOKIE_SECURE=true` and serve the application only over HTTPS.

To allow other machines on a CentOS host to reach Apache, open only the web
port in the host firewall:

```bash
sudo firewall-cmd --permanent --add-port=9091/tcp
sudo firewall-cmd --reload
```

Check the containers with `docker compose ps` and logs with
`docker compose logs -f api web`.

```bash
docker compose down
```


## Access PostgreSQL manually

The local database runs in the `shadcn-admin-db` Docker container and is
available to local tools at `localhost:5432`.

```bash
# Interactive SQL shell
docker compose exec -it shadcn-admin-db psql -U shadcn_admin -d shadcn_admin

# Execute a one-off query
docker compose exec db psql -U shadcn_admin -d shadcn_admin -c 'SELECT id, email, role FROM users;'

# Prisma's browser database UI
docker compose run --rm -p 5555:5555 api npm run db:studio

```

The compose password is for local development. In production, use a secret
manager and a restricted database account; do not publish `DATABASE_URL`.

## Tables

| Table | Purpose |
| --- | --- |
| `users` | Accounts, profile fields, roles, status, and password hashes |
| `sessions` | Hashed HTTP-only session tokens and expiry timestamps |
| `user_settings` | One preference record per user |
| `tasks` | Task work items with creator and optional assignee |
| `dashboard_metrics` | Imported or manually managed period-based measures, such as revenue |
| `activity_logs` | Auditable record of actions; dashboard activity feeds read from this |

The `dashboard` is not a table. `GET /api/dashboard` combines live task/user
counts, metrics, and activity logs. This avoids stale dashboard totals.

## API CRUD map

All routes below are prefixed with `/api`; browser requests use the HTTP-only
session cookie automatically. `users` and metric writes require an
`SUPERADMIN`, `ADMIN`, or `MANAGER` role.

| Data | Endpoints |
| --- | --- |
| Auth | `POST /auth/sign-up`, `POST /auth/sign-in`, `POST /auth/sign-out`, `GET /auth/me` |
| Tasks | `GET /tasks`, `POST /tasks`, `PATCH /tasks/:id`, `DELETE /tasks/:id` |
| Users | `GET /users`, `POST /users`, `PATCH /users/:id`, `DELETE /users/:id` |
| Settings | `GET /settings`, `PUT /settings/profile`, `PUT /settings` |
| Dashboard | `GET /dashboard`, `PUT /dashboard/metrics` |

## Manual CRUD examples

Run the following inside the `psql` shell. PostgreSQL converts unquoted enum
values as shown below. IDs are generated by Prisma (`cuid` strings), so direct
SQL examples use `gen_random_uuid()` only if your database has the relevant
extension. The safer approach is to copy an existing `id` value or use the API
for inserts that require generated IDs.

### Users

```sql
-- Read
SELECT id, username, email, role, status, created_at FROM users ORDER BY created_at DESC;

-- Update non-security fields
UPDATE users
SET first_name = 'Ada', last_name = 'Lovelace', updated_at = NOW()
WHERE email = 'admin@example.com';

-- Suspend rather than delete, so task history remains useful
UPDATE users SET status = 'SUSPENDED', updated_at = NOW()
WHERE id = '<user-cuid>';
```

Never insert a plaintext password into `users.password_hash`. Create accounts
through `POST /api/auth/sign-up`, or generate a bcrypt hash using the API
service tooling. Deleting a user cascades to their sessions/settings and may be
blocked by tasks they created; suspension is normally preferred.

### User settings

```sql
-- Read settings with account email
SELECT u.email, s.theme, s.font, s.notification_type
FROM user_settings s JOIN users u ON u.id = s.user_id;

-- Update settings for one account
UPDATE user_settings
SET theme = 'dark', font = 'inter', updated_at = NOW()
WHERE user_id = '<user-cuid>';
```

Use `PUT /api/settings` to create or update settings in application flows. It
uses an upsert, so every user has exactly one settings row.

### Tasks

```sql
-- Read
SELECT id, title, status, priority, assignee_id, due_date
FROM tasks ORDER BY updated_at DESC;

-- Update status
UPDATE tasks SET status = 'DONE', updated_at = NOW()
WHERE id = '<task-cuid>';

-- Delete (only when it is intentionally permanent)
DELETE FROM tasks WHERE id = '<task-cuid>';
```

For a new task, prefer `POST /api/tasks`; it sets `creator_id` from the
authenticated session and writes an audit record.

### Dashboard metrics

```sql
-- Read current metrics
SELECT key, value, period_start, period_end, metadata
FROM dashboard_metrics ORDER BY period_end DESC;

-- Insert or replace a monthly revenue metric
INSERT INTO dashboard_metrics (id, key, value, period_start, period_end, metadata, created_at, updated_at)
VALUES ('<new-cuid>', 'revenue', 45231.89, '2026-08-01', '2026-08-31', '{"currency":"USD"}', NOW(), NOW())
ON CONFLICT (key, period_start, period_end)
DO UPDATE SET value = EXCLUDED.value, metadata = EXCLUDED.metadata, updated_at = NOW();
```

Prefer `PUT /api/dashboard/metrics` for this operation. It validates the data,
requires an admin/manager role, and creates an activity log entry.

### Sessions and activity logs

```sql
-- Revoke all sessions for a user (forces sign-in again)
DELETE FROM sessions WHERE user_id = '<user-cuid>';

-- Inspect recent activity
SELECT action, entity, entity_id, user_id, created_at
FROM activity_logs ORDER BY created_at DESC LIMIT 50;
```

Do not manually create sessions: their tokens must be random, stored only in
an HTTP-only cookie, and the database stores their SHA-256 hash rather than the
raw token.

## Database backups

PostgreSQL stores its physical data in the Docker volume
`documents_app_postgres_data` (the exact prefix depends on the Compose project
name). Do not edit or selectively copy files from the volume's `_data`
directory. In particular, copying that directory while PostgreSQL is running
can produce an inconsistent backup. Use `pg_dump` instead.

Run the following commands from the directory containing `docker-compose.yml`.
Create a timestamped, compressed backup in PostgreSQL's custom format:

```bash
mkdir -p backups
docker compose exec -T db \
  pg_dump -U shadcn_admin -d shadcn_admin --format=custom \
  > "backups/shadcn_admin-$(date +%F-%H%M%S).dump"
```

If the Docker installation requires administrator privileges, use
`sudo docker compose` in place of `docker compose`. The shell creates the
backup file as the current user.

List a backup's contents to verify that PostgreSQL can read it:

```bash
docker compose exec -T db pg_restore --list \
  < backups/shadcn_admin-YYYY-MM-DD-HHMMSS.dump
```

Replace the example timestamp with the actual backup filename. A successful
command prints the backup's table of contents.

The database dump does not include cluster-wide roles and settings. Back those
up separately when they are managed by this PostgreSQL instance:

```bash
docker compose exec -T db \
  pg_dumpall -U shadcn_admin --globals-only \
  > "backups/postgres-globals-$(date +%F-%H%M%S).sql"
```

Copy backups to another server or encrypted object storage. A backup kept only
on the Docker host does not protect against host disk failure or loss.

## Restore a database backup

The following command restores a custom-format dump. `--clean` removes
matching existing database objects first, so this operation replaces current
application data and should be run only when a restore is intended:

```bash
docker compose exec -T db \
  pg_restore -U shadcn_admin -d shadcn_admin \
  --clean --if-exists --no-owner \
  < backups/shadcn_admin-YYYY-MM-DD-HHMMSS.dump
```

After restoring, check the API and database logs and verify that users, tasks,
and dashboard data are present:

```bash
docker compose logs --tail=100 db api
docker compose exec -T db \
  psql -U shadcn_admin -d shadcn_admin \
  -c 'SELECT COUNT(*) AS users FROM users;'
```

## Production database operations

Use a managed PostgreSQL provider's encrypted backups and point the API's
server-side `DATABASE_URL` at it for production. Run `npm run db:migrate` as a
deployment step before releasing a server version that depends on a migration.
